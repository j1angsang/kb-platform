# 知识图谱接入实现报告

> 目标：给现有 RAG 加一层实体关系图，解决跨文档关联与实体聚合两类查询。
> 结论先放这里：**图只做候选池扩充器，不做第三路召回，不做内容源。**
> 这一条决定了后面所有设计，也是唯一能让权限不被击穿的接法。

---

## 1. 先划清边界

"知识图谱"在这个项目里只做一件事：**告诉检索"还该看哪些 chunk"**。

不做的事，每条都有具体原因：

| 不做 | 原因 |
|---|---|
| 图作为第三路 RRF | `select_relevant_hits` 的 rrf 分支门控地板是 `max(SEARCH_MIN_SCORE, top_relevance - SEARCH_MAX_DROP) ≥ 0.80`，按余弦分标定。图候选没有向量分，会落到 RRF 归一化 `score`，量级完全不同 → 全被杀 |
| 图回填向量分再进 RRF | 多跳邻居与 query 的语义距离天然远（这正是需要图的原因），回填后依然过不了门控；放宽阈值会击穿"无答案拒答" |
| 实体携带正文/属性/部门 | 实体是跨文档合并的（"年假"聚合人事部/技术部/财务部三份文件）。带单一部门字段会在 N 个部门间分裂成 N 份；带正文则成为绕过权限的新出口 |
| 社区摘要（GraphRAG L2） | 增量更新是死穴，且当前语料规模撑不起收益，见 §9 |
| 把 middleware 拆成显式图节点 | 项目已经是图（`create_agent` + 6 个 middleware + `can_jump_to` 条件边），再"图工程化"是纯重构、零能力增量 |

---

## 2. 存储：用 PostgreSQL，不上 Neo4j

准确说法是**能上，但代价不对等**。三条理由与历史决策无关：

**规模。** 全量回填后约 100 实体 / 150 条边。Neo4j 的价值区间是"亿级节点 + 4 跳以上深链遍历"，
这个量级在 PG 邻接表上跑 2 跳递归 CTE 是毫秒级，性能收益为零，成本是一个新容器 + 备份 + 监控
+ 连接池 + 版本升级。

**行级权限与图遍历，模型本身冲突。** Neo4j 没有 PG 那样的原生行级安全。要在多跳里注入
权限条件，Cypher 得写 `WHERE ALL(n IN nodes(path) WHERE n.department = $dept)` —— 但**这个
条件根本写不出来**：实体节点跨部门合并，上面没有单一 `department`。于是只剩两条路：
权限冗余进图（实体分裂，图退化），或每跳跨库回 PG 查。

**丢掉 `ON DELETE CASCADE` 这个免费的正确性。** PG 里 `graph_relations.chunk_id` 挂
FK CASCADE，`delete_by_file` 一执行边自动清。Neo4j 没有外键约束，双写后删文件要手写清理顺序，
漏一条就是幽灵召回：图返回已删除的 chunk_id，回表查不到，静默丢弃，还会污染 graph-only 指标。

代价对比很直白：**递归 CTE 10 行，Cypher 3 行 —— 省 7 行代码换一个数据库。**

### 什么时候才该换

| 判据 | 本项目 |
|---|---|
| 需要 4 跳以上路径查询（股权穿透、供应链溯源） | ❌ 查询深度 ≤2 |
| 需要内建图算法跑百万级节点 | ❌ 实体百级 |
| 图本身是主数据模型，不是文档的附属索引 | ❌ 是附属索引 |
| 有独立运维能力 | ❌ 单实例 |

佐证：微软 GraphRAG 官方实现的索引产物是 Parquet，查询时在内存建图，Neo4j 只是可选导出目标。

## 3. 数据模型

```
graph_entities(id, canonical_name, type, aliases, name_embedding, mention_count, status, merged_into)
graph_relations(id, subject_id, predicate, object_id, value, chunk_id, confidence)
graph_jobs(id, doc_id, state, attempts, last_error, next_run_at)
knowledge_docs += kg_status, kg_error, kg_entity_count
```

三个设计点：

**`chunk_id` 上的 FK CASCADE 是权限锚点，也是正确性来源。** 删文件 → 删 chunk → 级联删边，
不用在 indexer 里手写清理顺序。

**`value` 字段砍掉一半实体爆炸。** 宾语是实体时填 `object_id`，是字面值（金额/天数/比例）时
填 `value` 不建节点。否则图里会塞满 `500元`、`30天`、`80%` 这种一次性名词。

**`graph_jobs` 必须独立成表。** `IndexJob.doc_id` 是 `unique=True`，
`crud/knowledge.py:claim_index_job` 靠「条件 UPDATE + rowcount」做并发判定。改成
`(doc_id, stage)` 复合唯一会同时破坏唯一约束语义和 claim 逻辑。独立表零风险，两套租约互不干扰。

## 4. 抽取：受限 schema，不赌开放域

```python
ENTITY_TYPES = (department, position, role, policy, process, system, form, org)
PREDICATES  = (适用, 审批, 归属, 依据, 包含, 负责, 替代, 标准为, 提交至, 发放)
```

开放域抽取的噪声率高到不可用：模型会把"以上""具体""相关"当实体，造出"关于""涉及"这种
无边语义的谓词。噪声边会污染实体链接的向量空间，让消融实验永远看不出结论。

**部门名不交给模型猜。** `config/departments.py:ALLOWED_DEPARTMENTS` 是唯一真相，词典命中
直接锁定 canonical name（`normalize_department` 用包含关系匹配，"技术部（研发中心）"归到
"技术部"）。这类确定性信息没有理由赌概率。

**跳过两类块**（`rag/graph/pipeline.py:_selectable`）：
- `sheet` 非空的 xlsx 表格行块 —— 结构化数据该走 Text2SQL，硬抽只会得到一堆列名当实体
- `source=ocr_lowconf` —— 文字本身不可靠，抽出来的实体名会污染消歧的向量空间

**解析失败不"尽力修复"。** `parse_triples` 对不合约的行直接丢弃：修出来的实体名会以错误形态
进图，而实体链接会持续放大这个错误。丢弃只是少一条边。

## 5. 消歧：三层，最后一层必须有人

图的成败在这一步，不在抽取。三层策略：

| 层 | 手段 | 阈值 | 作用 |
|---|---|---|---|
| 1 | 精确匹配 `canonical_name` / `aliases`（数组语义，避免"技术部"命中"技术部A"） | — | 覆盖绝大多数重复提及 |
| 2 | 名称向量近邻（pgvector `<=>`，同 type 内比较） | `KG_MERGE_MIN_SCORE=0.96` | 兜住"直属上级"→"直属领导" |
| 2b | 词面互为子串 + 稍低向量分 | `KG_MERGE_SUBSTRING_SCORE=0.90` | 兜住"印章使用"→"印章" |
| 3 | 人工合并/拆分（`/graph/entities/merge`、`/split`） | — | 自动判错的兜底 |

**单靠余弦判不出来，必须再加一道词面证据。** 实测踩过的错：

```
销售经理     -> 销售总监        0.9583   ✗ 两个不同职位
考勤和差旅制度 -> 考勤管理制度    0.9343   ✗ 两份不同制度
财务总监     -> 财务负责人       0.9447   ✗ 可能是两个角色
直属上级     -> 直属领导        0.9731   ✓ 同一个
印章使用     -> 印章           0.9313   ✓ 子串关系，同一个
```

中文职位名和制度名的字面相似度与语义相似度严重脱节。0.92 这种"看起来合理"的阈值，
会把经理并进总监、把两份制度并成一份 —— 而且**合并是不可见地污染下游**：错并之后，
"销售经理的审批权限"会沿着"销售总监"的边扩出去，答案错得毫无痕迹。

所以是两道门：纯向量必须过 0.96；词面互为子串才允许降到 0.90。
子串是强证据（"印章使用"里确实有"印章"），而"经理/总监"只差一个字却不是子串关系。

第 3 层不能省：阈值调高会漏合并（图碎片化），调低会错合并，两头都不可能一次调准。
合并保留 `merged_into` 而不是物理删除，因为人工判断会错，必须可追溯、可拆分。

**type 限定必须加**：`"技术部"(department)` 和 `"技术"(system)` 在不同类型里不能互相合并。

## 6. 检索接入：图只扩池

```
query
 ├─ 向量 top20 ──┐
 ├─ BM25 top20 ──┤
 │               ├→ RRF → 候选池 (RERANK_TOP_N + KG_CANDIDATE_TOP_K)
 └─ 实体链接 → 多跳(≤2) → chunk_id → 权限 SQL ─┘
                                    ↓
                        cross-encoder rerank（绝对分）
                                    ↓
                        RERANK_MIN_SCORE 门控（一行未改）
```

**为什么这样接是对的：** `rerank_score` 是 cross-encoder 对 `(query, chunk)` 直接打分的
绝对分，不依赖候选来自哪一路。图找来的是真相关内容，rerank 自然给高分；不相关就被门控拒掉。
**图的唯一职责是"把原本进不了候选池的 chunk 送进来"，判断权归 rerank。**

三个直接收益：
- `select_relevant_hits` **一行未改**
- `SEARCH_MIN_SCORE` / `SEARCH_MAX_DROP` / `RERANK_MIN_SCORE` **全部不用重标定**
  （`_relevance_score` 是请求内相对分，扩池会改变分布；`rerank_score` 是绝对分，不受影响。
  这两个阈值性质不同，别混）
- 图链错的实体，扩出来的噪声 chunk 会被 rerank 杀掉 —— 这是敢把链接阈值放宽到 0.82 的底气

**硬依赖：`KG_ENABLED` 必须要求 `RERANK_ENABLED`。** 关掉 rerank 时图候选没有绝对分，
只能回落 `_relevance_score` → 回到门控全杀。`config/settings.py` 启动即校验，对齐
`LLM_SUPPORTS_VISION=false` 的先例。

**唯一改主链路的点**：`rag/store.py:search()`。`agents/graph.py`、`tools/knowledge_tools.py`、
`rag/fusion.py`、`docker-compose.yml` **都不用改** —— 图通道藏在 store 层，
`rag_hook` 和 `search_knowledge` 两个调用点自动获得能力。

## 7. 与入库解耦：先可检索，再建图

图抽取是分钟级 LLM 调用。塞进 `_index_document_inner` 会让"入库成功"从秒级变成分钟级，
而 `index_status=ready` 才能被检索到 —— 等于把检索可用性绑在建图进度上。

```python
doc.index_status = "ready"          # 先落库，立刻可检索
if KG_ENABLED:
    doc.kg_status = "pending"
    await graph_crud.enqueue_graph_job(db, doc.id)
await db.commit()
```

配套三条：
- `kg_status` 默认 `skipped`：部署不给存量文档自动排队，回填必须显式触发
- **独立锁**：`_graph_locks` 与 `_doc_locks` 分开。图要跑几分钟，共用一把锁会把入库整个堵死
- **独立状态机**：图失败只写 `kg_status=failed`，绝不触碰 `index_status`

## 8. 踩过的坑

这一节是全文最有用的部分，全是实测撞出来的。

### 8.1 批量 INSERT ... ON CONFLICT 的 rowcount 不可靠

```
graph.store file_id=1 chunks=1 entities=6 edge_rows=4 written=-1
```

`psycopg` 对批量 upsert 返回 `rowcount=-1`。日志和指标直接失真。
改成 `.returning(GraphRelation.id)` + `len(result.all())`。

### 8.2 FK CASCADE 在重入库时不触发，旧边必须显式删

`chunk_id` 是确定性 id（`f"{file_id}:{seq}"`），重入库走的是 `on_conflict_do_update` 而不是
`delete + insert` —— 行没被删过，级联就不会触发，旧边会混在新 chunk 上。

所以 `delete_edges_by_file` 必须在抽新一轮前显式调用。这是"确定性 id + upsert"这个设计的
隐性代价，只靠 CASCADE 会漏。

### 8.3 泛实体污染：一个"员工"毁掉整条图通道

实测：

```
Q: 员工生病要请长假
  entities: [('员工', 'role', 'dict', 0.99)]
  chunks:   [('5:0', 0, '# 报销管理制度 ...')]
```

"员工"在 query 里字面出现，词典路 0.99 命中，于是图扩出的是**"员工"这个实体的全部证据** ——
和"生病请假"毫无关系。

修法：`KG_LINK_STOPWORDS`（员工/公司/部门/领导/同事…）。这类词出现在几乎每个 query 里，
对定位零区分度，必须在**链接期**过滤。只影响链接，不影响抽取 —— 实体本身仍在库里，
只是不作为检索入口。

### 8.4 链接阈值 0.86 太高，实测标定到 0.82

```
员工生病要请长假  → 病假 0.8497   （0.86 挡在门外）
新来的同事多久转正 → 转正 0.8530   （0.86 挡在门外）
```

原来的 0.86 恰好把换说法全部挡掉，图通道等于没开。降到 0.82 后这两类都能命中。
不敢再低：0.75 一档会把"考勤管理制度"（0.7535）这种弱相关实体也拉进来，池子被噪声占满。

**敢放宽的前提是 rerank 绝对分兜底**，这条与 §6 互相支撑。

### 8.5 自动合并阈值：三次迭代才收敛

这是整个改造里唯一返工两次的地方，值得完整记录。

**第一版 0.92**（直觉值）。全量回填后日志里出现：

```
销售经理     -> 销售总监        0.9583   ✗ 两个不同职位
考勤和差旅制度 -> 考勤管理制度    0.9343   ✗ 两份不同制度
财务总监     -> 财务负责人       0.9447   ✗ 可能是两个角色
```

**第二版 0.96 + 子串 0.90**。重跑后又出现：

```
销售经理 -> 销售主管   0.9744   ✗ 不同职级
财务     -> 财务负责人  0.9022   ✗ 子串规则放行，但"财务"是职能不是职位
```

关键观察在第二版才看清：

```
销售经理 -> 销售主管    0.9744   ✗ 不该并
直属上级 -> 直属领导    0.9719   ✓ 该并（同义词）
```

**这两个分数几乎一样，余弦分根本分不出来。** 中文职位名/制度名的字面相似度与语义相似度
严重脱节，调阈值这条路本身走不通 —— 调高会漏"上级/领导"，调低会并"经理/主管"。

**第三版 0.98 + 子串且短词 ≥ 3 字**，并且明确了价值判断：

> **错并的代价远大于漏并。** 漏并只是图碎片化、多跳走不通；错并会让下游推理沿着错误的边
> 扩散，给出看起来合理但完全错误的答案，且无法事后拆分 —— 边已经挂到 target 上，
> 原始写法只留一个 alias 字符串，语义已经丢了。

所以自动合并只保留"几乎肯定相同"的情形（字面全同、或长词包含短词且短词够长），
其余全部交给人工合并界面。实测 10 个已知 case 全部判定正确。

**这件事真正的教训不在阈值数字，在验证顺序：**

1. 如果先跑完 44 份再看结果，等于用整批数据验一个错误参数 —— 第一次我就是这么干的。
2. 正确顺序是先跑 3~5 份、**逐条看抽出来的边和每一条合并日志**。第一次我跑了 3 份、
   看了 19 条边，但只检查"边本身对不对"，没检查"实体有没有被错误合并"。
3. 合并日志是 INFO 级别、混在几十行里，很容易漏。**回填脚本应该把合并动作列成单独摘要**，
   让人一眼看到"这次并了哪几对"，而不是去 grep 日志。

### 8.6 图模块与 store 的循环导入

`rag/store.py` 要 import 图通道，`rag/graph/store.py` 要用 `PgVectorStore._permission_clause`
和 `_metadata`。模块级互相 import 直接成环。

修法：`_store_deps()` 函数内延迟导入，并在注释里写清"必须复用同一份实现，复制一份必然漂移"。
权限表达式只有一处实现，是这个项目从第一天就守住的东西。

### 8.7 邻域查询用 inner join 丢掉了一半关系

`entity_neighbors` 原本写的是：

```python
select(GraphRelation, GraphEntity).join(GraphEntity, GraphEntity.id == GraphRelation.object_id)
```

字面值边（`人事部 --发放--> "offer"`）的 `object_id` 是 NULL，inner join 直接把它们整条丢掉。
现象是"邻域看起来少了一半关系"，而且很难发现 —— 因为返回的边本身都是对的，只是不全。

改成 `outerjoin`，并在构造 edge 时对 `other is None` 兜底（`other_id/other_name/other_type`
都置空，`value` 照常给）。

**这是"`value` 字段省掉一半实体"这个设计的配套代价**：省掉了节点，就必须在每一处关系查询
里都记得处理 object 为空的情况。漏一处就是静默丢数据。

### 8.8 拆分实体是空转：查回来的还是那条 merged 行

`split_entity` 原本先 `INSERT ... ON CONFLICT DO NOTHING`，再按名字查 id 返回。
但合并时源实体是**标 `status='merged'` 保留**的（为了可追溯），所以：
- insert 被 on_conflict 挡掉
- 查回来的是那条 `status='merged'` 的旧行
- 接口返回了一个 new_entity_id，看起来成功，实际什么都没改

实测：`POST /graph/entities/5/split {"alias":"OA系统"}` 返回 `new_entity_id=3`，
但 3 仍然是 `status=merged`，链接时 `entity_names` 只取 `status='active'`，等于这个实体不存在。

修法：查到行之后判断 `status == 'merged'` 就恢复成 `active` 并清空 `merged_into`。

**这条 bug 的教训**：我在 §5 写了"合并保留 merged_into 而不是物理删除，因为要可追溯、可拆分"，
但拆分路径根本没实现恢复 —— **承诺和实现脱节，比没承诺更糟**。写"可逆"就必须测一次逆向操作。

**已知限制**：拆分只恢复实体本身，**不回溯边**。合并时边已经混到 target 上，
无法区分哪些原本属于 source（原始三元组没留快照）。要在意这点，就得在合并前把
`(subject_id, predicate, object_id, chunk_id)` 存一份归档表。

### 8.9 FastAPI 0.139 的路由是惰性注册的

`app.routes` 里看到的是 `_IncludedRouter` 对象，没有 `.path`，直接数路由会以为没注册上。
要用 `app.openapi()["paths"]` 才会展开。排查路由缺失时别被这个骗了。

### 9.1 图建设

| 指标 | 值 |
|---|---|
| 处理文档 | 44 份（41 成功，3 份 LLM 超时失败） |
| 实体 | 299 |

| 自动合并 | 1 次（`合同审批流程 → 销售合同审批流程`，子串正确合并） |
| 耗时 | 690 秒（约 400 次 LLM 调用） |

### 9.2 检索指标：图通道净贡献为 0

```
配置            多跳/聚合Recall@5  对照题Recall@5  MRR    avg_noise  拒答率  graph_only_rate  P95
graph_off       1.0               1.0            0.775  0.2917     1.0    0.0              1653ms
graph_on        1.0               1.0            0.775  0.2917     1.0    0.0              258ms
```

**两列完全一样。** 图通道在 15 题中的 11 题上召回了候选（最多一题 13 个 chunk），
但 `graph_only_total = 0` —— 所有图召回的 chunk，向量 top20 或 BM25 top20 都已经命中。

这不是实现失败，是**语料结构性原因**：

> 这套语料是"1 文档 1 chunk / 短文档单主题"。任何被实体连到的 chunk，其正文里必然
> 写着实体名（否则那个实体不可能从这份 chunk 里抽出来），所以 BM25 必然也能召回它。

换句话说：**图要产生独占价值，需要"关系存在但字面不重叠"的语料**。例如某份文档里
只有"用车申请"而没有"OA"，但图里存在 `用车申请 --提交至--> OA` 这条边 ——
这时 query"OA 上能提交什么"才会出现 graph_only。当前语料没有这种结构。

### 9.3 权限隔离：对照实验通过

这是整套方案最核心的安全验证，分两条路径说，因为它们的防线位置不同。

**路径一：检索期（真正会生效的防线）**

query「技术部的数据库变更怎么审批」，技术部文档 `技术部-数据库变更审批.md` 是
**非共享**（`is_shared=false`）。直接调 `neighbor_chunks` 做对照：

```
department=None        chunks=8   含 33:0（技术部-数据库变更审批）   ← 不过滤，能看到
department='人事部'     chunks=5   不含 33:0                        ← 被挡住
department='技术部'     chunks=8   含 33:0                          ← 正常可见
```

员工在 chat 里提问走的就是这条路径。**结论：图通道复用同一条 `_permission_clause`，
没有产生越权出口。** 这是把图放在 store 层而不是图数据库里的最大收益 ——
权限只有一处实现，图没法绕过它。

**路径二：管理端证据（当前不会剔除任何行，但保留）**

`/graph/*` 由 `require_manager` 挡掉 employee；而 `can_view_all_departments` 对
leader/admin 都返回 True（与 chat 检索同一套语义，leader 本来就跨部门）。两个条件叠加，
`routers/graph.py` 里那段证据过滤**在当前入口下恒为真**。

这段代码保留，理由是将来若把图谱开放给员工，它会立刻生效，不需要重写一遍权限逻辑。
但文档里必须写清楚它现在不起作用 —— 否则读代码的人会以为"领导看证据被限制在本部门"，
那是错的，实测 30 条边全部可见。

> 教训：我曾按"leader 只能看本部门"写注释，实测发现 leader 证据全可见，
> 才发现 `can_view_all_departments` 的语义是 `is_manager`（含 leader）。
> 注释里的想当然比代码 bug 更容易骗人。

### 9.4 零回归

|---|---|---|---|---|

| weighted + rerank on | 1.0 | 1.0 | 1.0 | 5/5 |

### 9.5 怎么读这个结果

**指标没涨，但这不代表活白干。** 分层看：

| 层面 | 结论 |
|---|---|
| 工程正确性 | ✅ 图建对了、权限挡住了、零回归 |
| 检索指标 | ⚪ 净贡献 0，原因是语料没有多跳场景 |
| 可解释性 | ✅ 能回答"为什么召回这份文档"——沿实体链路逐跳展示，向量检索给不出这个 |
| 治理能力 | ✅ 实体浏览、人工合并/拆分、链接预览，是后续调优的唯一入口 |

如果目标只是"Recall 涨几个点"，这套语料下做不出来，也不该硬做。真正的价值在
"关系可解释"和"实体可治理"——这也是为什么 §9.2 的 0 要如实写出来：
一个不敢报 0 的评测，报出来的正数也不可信。

### 9.6 什么条件下值得继续投入

按优先级：

1. **语料先变成"长文档 + 跨文档引用"**。一份 50 页的制度手册里有几十个实体，
   实体间的边才有多跳价值；现在每份文档只有 1 个 chunk，图退化成"文档标签"。
2. **加"关系但无字面重叠"的测试集**，专门造 graph_only 场景，验证通道确实有效。
3. 再考虑 L2 社区摘要（全局总结类问题）。

第 1 条不满足之前，继续加图的功能都是空转。

---

## 10. 局限

- **语料规模决定图的上限。** 当前 44 份文档、130 个文本块，且每份主题单一，向量检索已经很够用。
- **同义写法仍需人工。** "生病"→"病假"这类没有字面重叠的，向量能在 0.82 兜住；但更远的
  换说法（"身体不舒服"）连不上。真正的解法是抽取阶段产出 `aliases`，成本更高。
- **L2 社区摘要未做。** 全局总结类问题（"公司有哪些福利"）仍然答不好，但那是 `top_k=3` 的
  结构性问题，不是图的锅。
- **单实例假设。** `graph_jobs` 的租约和 `_graph_locks` 都假设单进程；多 worker 需要把锁
  换成 PG advisory lock。
- **自动合并已收紧到接近"字面全同"。** 代价是漏合并多，靠人工界面补。这是刻意的取舍，
  见 §8.5。
