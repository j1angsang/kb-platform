# 检索融合改造报告：Weighted → RRF

- 日期：2026-10-19
- 范围：只改检索融合层与门控，不动数据库、上传、审核流、Agent 钩子
- 默认值：`SEARCH_FUSION=rrf`；`SEARCH_FUSION=weighted` 可一键回滚

## 1. 一句话结论

把“向量分 + BM25 归一分的加权求和”改成“只看名次的 RRF”，同时把**排序分**和**相关性门控分**拆开：RRF 负责排序，`_relevance_score` 和 `rerank_score` 负责“这条内容够不够相关”。这样既换掉了对 BM25 最大值归一化的依赖，也没有破坏原来的拒答语义。

## 2. 为什么改

原来的加权融合是：

```text
bm25_norm = bm25 / max_bm25(本次查询)
fused     = 0.6 * vector_score + 0.4 * bm25_norm
BM25-only 再乘 0.95
```

它有三个真实问题：

1. **BM25 用“本次查询的最大值”归一**：一个强命中会把其他 BM25 分数压扁，跨查询不稳定；
2. **向量分集中在 0.83~0.95**：加权后仍然是向量主导，BM25 只能微调排序；
3. **`0.95` 是魔法常数**：没有标定依据，只是让 BM25-only 不至于太靠后。

RRF 的出发点是：两路检索的分数量纲根本不同，不要强行归一化，只看名次：

```text
rrf(d) = Σ_i  w_i / (k + rank_i(d))     # rank 从 1 开始，k 常用 60
```

它的优点是**不依赖分数尺度**，换 embedding 模型、换 BM25 实现都不用重标权重；代价是**丢掉分数幅度**，不能直接拿 RRF 分数做绝对阈值。

## 4. 三个分数，各干一件事

| 字段 | 来源 | 用途 |
|---|---|---|
| `score` | RRF 分数按当前最大值归一化到 0~1 | 排序、展示；**不要拿它套 0.80/0.015** |
| `_relevance_score` | 沿用原加权分（向量分 + BM25 归一） | 相关性门控；保持原来的 `SEARCH_MIN_SCORE` / `SEARCH_MAX_DROP` 语义 |
| `rerank_score` | cross-encoder | 开启重排时的最终门控；独立字段，不覆盖 `score` |

为什么要拆开？因为 RRF 的典型分数是 `0.016~0.033`（k=60、两路各 top20），而原阈值 `SEARCH_MIN_SCORE=0.80` 是按余弦分标定的。直接换融合会把所有结果判成不相关，属于“算法换了、门控没换”的典型事故。

## 5. 评测

### 5.1 题集

`eval/eval_set.jsonl`，共 21 题：

- 8 道知识问答（年假、报销、差旅、考勤、IT、采购、调休、投诉）；
- 8 道字面查询（金额/时限/故障词等）；
- 5 道无答案/超范围题（食堂、班车、年会、天气、写代码）。

题集基于 `seed_enterprise_data.py` 的公开种子文档，不包含内部评测报告。指标定义见 `eval/README.md`。

### 5.2 结果（本机，现有库，旧切分）

固定 `top_k=5`、入选 `top3`，只变融合与 rerank：

| 配置 | 知识题 Recall@5 | 字面题 Recall@5 | 知识题 MRR | 知识题噪声 | 无答案拒绝率 |
|---|---|---|---|---|---|
| weighted + rerank off | 1.0 | 1.0 | 1.0 | 0.0 | 0/5 |
| rrf + rerank off | 1.0 | 1.0 | 1.0 | 0.0 | 0/5 |
| weighted + rerank on | 1.0 | 1.0 | 1.0 | 0.0625 | 5/5 |
| rrf + rerank on | 1.0 | 1.0 | 1.0 | 0.0625 | 5/5 |

### 5.3 怎么解读

1. **有上限效应**：题集和语料都小，两种融合都拿满分。这份数据不能证明 RRF 提升了召回，只能证明“没有退化”。
2. **无答案题只靠 rerank 拒答**：关掉 rerank 时 weighted 和 RRF 都是 0/5；开启后 5/5。结论是**门控的关键是重排，不是融合**，这个发现比“RRF 提升 X%”更真实。
3. **RRF 的价值在工程属性**：不依赖 BM25 最大值归一化、不依赖两路分数量纲、换检索器不用重标；同时保留 weighted 回退，方便 A/B。
4. **延迟不能直接比**：P95 包含 embedding、数据库、rerank 和缓存命中顺序；本次运行里先跑的配置更冷，不能把差异归因于融合算法。

## 6. 简历怎么写

可以写“改造 + 评测 + 回滚”，不要写“RRF 提升召回”，因为数据不支持。

### 版本 A（技术点）

- 将混合检索的加权分数融合升级为 **RRF（倒数排名融合）**，新增 `SEARCH_FUSION` 配置与 `weighted` 回滚路径。
- 解决 RRF 分数（0.01~0.03）与原有 `0.80/0.015` 门控阈值量纲不兼容的问题：**排序与置信度解耦**，RRF 只排序，`_relevance_score` / `rerank_score` 负责门控。
- 新增 21 题检索评测集与脚本（Recall@k、MRR、nDCG、噪声、拒绝率），完成 weighted/RRF × rerank on/off 四组 A/B。

### 版本 B（结果导向）

- 改造前：BM25 依赖本次查询最大值归一，融合权重难以跨语料复用；改造后：RRF 只看名次，换检索器/embedding 不需重标融合参数。
- 在 21 题评测集上完成回归：两种融合 Recall@5 均为 1.0，确认 RRF 未降低召回；无答案题在 rerank 开启时拒绝率 5/5，关闭时 0/5，定位出门控关键路径。

### 版本 C（STAR）

- **S**：混合检索用加权分数融合，BM25 归一化跨查询不稳定，且门控阈值和融合分数量纲耦合。
- **T**：换成更通用的 RRF，同时不破坏拒答与图片通道。
- **A**：实现 RRF 纯函数；保留 weighted 回滚；把排序分、相关性分、重排分拆开；补 21 题评测集与脚本。
- **R**：Recall@5 保持 1.0，无退化；无答案拒绝率在 rerank 开启时 5/5；形成可复跑的回归基线。

### 不要写

- “RRF 使召回率提升 X%”——本次数据没有提升；
- “支撑高并发/生产级”——当前是 40 篇文档、单机；
- “自研 RRF 算法”——RRF 是公开方法，重点是你怎么接入、怎么门控、怎么评测。

## 7. 面试问答

**Q：为什么用 RRF，不用加权？**
A：加权要先把 BM25 归一到向量分的尺度，但 BM25 的最大值依赖本次查询，换语料/换模型要重标；RRF 只看名次，对异构检索器更稳。代价是丢掉分数幅度，所以不能拿 RRF 分数做绝对阈值。

**Q：RRF 分数这么小，原来的 0.80 阈值怎么办？**
A：不能直接套。我的做法是三个分数分开：`score` 是归一化 RRF 用于排序/展示，`_relevance_score` 沿用原加权分做门控，`rerank_score` 做最终门控。这样不用改原来的拒答阈值。

**Q：为什么还保留 weighted？**
A：A/B 和回滚。RRF 是更通用的默认值，但在小语料上没有可观测增益；保留 weighted 可以灰度、对比、出问题一键切回。

**Q：RRF 一定更好吗？**
A：不一定。RRF 是 rank-based，丢掉置信度；如果一路检索器明显更强，等权 RRF 会拖后腿，可以用 weighted RRF。我的评测集太小，不能证明更好，只能证明不退化。

**Q：为什么不用 LangChain 的 `EnsembleRetriever`？**
A：它是 retriever 级封装，要求两路都是 `BaseRetriever` 并返回 `Document`；我的向量检索带部门权限 SQL 下推、图片通道，BM25 是内存索引，还要保留 `_vector_score` / `rerank_score` 做门控。套进去要额外包两层，还会丢字段；RRF 只有十几行，纯函数更好测、更好讲。

**Q：如果数据量扩大 10 倍，这套还成立吗？**
A：融合层不变，RRF 的计算是 O(候选数)，可以忽略；瓶颈会变成向量检索、BM25 全量重建和 embedding 调用。BM25 目前是进程内全量重建，多实例会不一致，届时要换独立检索服务或按租户分片。
