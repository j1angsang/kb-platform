# Agent 七维评测

> 一年 Agent 开发，十年评测。这话不夸张 —— Agent 的失败大多不是"答案错了"，
> 而是"过程错了但答案碰巧对"。只看最终回答的评测，会把这些全放过。

## 0. 为什么不能只看结果

拿一个真实例子说明。用户问「你好我的年假还有多久」：

- 检索召回：《请假与休假管理规定》，BM25 第 1 位，rerank 0.708
- 门控：低于 `RERANK_MIN_SCORE=0.9`，被丢弃
- 模型看到"没有资料"，回答：**"知识库里没有年假政策"**

从"答案对不对"看，这题答错了。但错在哪一层？如果不拆开看，很容易归因成"模型不行"，
实际上模型只是忠实地复述了它拿到的信息 —— **错在门控把"部分相关"当成了"不相关"**。

七维评测就是把"错在哪一层"变成可测的数字。

## 1. 七个维度

| # | 维度 | 测什么 | 实现 | 本机实测 |
|---|---|---|---|---|
| 1 | 过程管控 | 该调的工具有没有调、有没有多调/失败 | `tool_trace` 与 `expect_tools` 比对 | 1.0（2 题适用） |
| 2 | 召回完整性 | 应召回的**全部**资料是否都进了上下文 | `expected_files` ⊆ `sources` | 1.0（6 题适用） |
| 3 | 忠实度 | 回答里有没有资料不支持的断言 | LLM judge 逐句查无据 | 1.0（0 ungrounded） |
| 4 | 工具真实性 | 工具失败是否被"已完成"话术掩盖 | 失败调用 × 完成类措辞 | 1.0 |
| 5 | 稳定性 | 同问多次结果是否一致 | 来源 Jaccard + 答案 Jaccard | 来源 1.0 / 答案 0.49 |
| 6 | 成本效率 | 延迟、token、工具调用次数 | `usage` 解析 + 计时 | P50 3.7s / P95 5.1s、2.3k token |
| 7 | 安全权限 | 越权/注入/隐私是否挡住且不泄漏 | 拒答判定 + 关键词泄漏扫描 | 1.0、应拒答题拒答率 1.0 |

### 维度 2 的关键：不是"召回了没有"，是"召回全了没有"

笔记里那个书包的例子是对的：描述有 5 条，只召回 4 条，模型照样能拼出一个合理答案。
**答案看着对，过程是残缺的。** 所以这一维只认"应召回集合 ⊆ 实召回集合"，
不看 top1 命中。

当前题集是文件级标注（一份文档即一个 chunk），所以算的是文件级完整性。
要做 chunk 级，需要把 `expected_files` 换成 `expected_chunk_ids`。

### 维度 3 的证据来源必须包含工具输出

第一版只拿 RAG 检索结果当证据，结果把 Text2SQL 的正确回答判成"无据" ——
因为查数据库得到的 8 人，文档里当然没有。

改法：`collect_evidence` 收集两路 —— 文档检索结果 + `trace` 里**成功**的工具输出。
失败的工具输出不算证据（那是错误信息，不能拿它支撑结论）。

### 维度 4 不能信 `ToolMessage.status`

工具内部 `try/except` 后仍返回字符串时，`ToolMessage.status` 是 `success`，
content 却是 `工具执行失败：Request timed out.`。

第一版按 status 判定，把"工具超时 + 模型编数字"判成了完全正常。
现在复用 `agents/graph.py:_tool_ok()` 看内容，软失败才识别得出来。

### 维度 5 的两个数要分开读

- **来源 Jaccard = 1.0**：三次召回的文档完全一致 → 检索链路是确定的
- **答案 Jaccard = 0.49**：措辞波动大 → 生成有随机性

这两个数含义完全不同。来源稳定说明"系统行为可复现"，答案波动是 LLM 的固有特性
（即使 temperature=0，上游也不保证逐字一致）。用答案 Jaccard 单独衡量"系统不稳定"是误读。

## 2. 这套评测抓到的真问题

这一节比指标本身值钱。

### 2.1 「知识库里没有年假政策」（幻觉，已修）

见 §0。修法两层：

1. **门控加弱相关兜底**（`rag/store.py`）：强相关一条都没有时，若 top1 ≥ 0.55 且领先第二名 ≥ 0.20，
   注入一条并打 `_weak_evidence` 标记。标定数据：

   | 场景 | top1 | margin | 处理 |
   |---|---|---|---|
   | 股票期权（无答案） | 0.233 | 0.052 | 不注入 |
   | 竞争对手工资（无答案） | 0.330 | 0.094 | 不注入 |
   | 年假还有多久（部分相关） | 0.708 | 0.354 | 注入 |
   | 年假能攒到明年吗 | 0.884 | 0.522 | 注入 |

2. **注入侧说明资料性质**（`services/prompt_guard.py:WEAK_EVIDENCE_HINT`）：
   告诉模型"这是最接近的资料但不一定直接回答问题；讲制度 + 指出个人数据另查；
   禁止断言知识库里没有相关政策"。

修后回答：

> 关于年假制度，规定如下：入职满 1 年 5 天、满 3 年 7 天、满 5 年 10 天[1]
> 不过，你**个人**还剩多少天年假，属于个人考勤数据，知识库里只有制度规定，没有你的余额记录。
> 建议登录 OA 查看，或向人事部核对。

同时把"没检索到"的拒答话术从「知识库中没有与用户问题相关的内容」改成
「本次检索没有找到与该问题直接相关的材料……不要断言该制度不存在」——
原话术会被模型加工成"没有 X 政策"，那是个它并不知道的结论。

### 2.2 工具超时后模型照样给数字（已加约束）

`query_employee_stats` 超时返回失败，模型仍然答「技术部共有 8 名员工」。

修法：工具失败时返回的不只是错误信息，还要明确禁止推测：

```
查询失败：{原因}。本轮没有拿到任何数据，请如实告知用户查询失败、建议稍后重试；
禁止根据常识、上文或历史对话推测具体人数、比例或排名。
```

顺带把 Text2SQL 的 LLM 超时从 15s 提到 30s —— 实测上游偶发 15.4s 才返回。

### 2.3 数据口径不一致（记录，未改）

`analytics.v_employee_directory` 有 17 人（技术部 8），`employees` 表有 10 人（技术部 10）。
Text2SQL 只暴露前者，所以「技术部多少人」答 8 是**在该口径下正确的**。

**这是评测题目标错，不是产品 bug。** 但它暴露了一个真实隐患：两套员工数据并存且不一致，
哪天报表和系统对不上，排查会很痛苦。建议确认哪套是权威来源，另一套下线或加同步校验。

### 2.4 编造制度名（记录，未修）

a-14「销售折扣需要谁审批」，模型输出了《销售管理制度》第五章第二十二条 ——
**这个名字和条款号在语料里不存在**，是拼出来的。

它同时做对了一件更值钱的事：发现两份材料的审批口径不一致，主动指出并建议以正式制度为准。
所以这题判 `partly` 而不是 `ungrounded`。

## 3. 局限

- **题集只有 15 题**，且集中在人事/财务/销售三类，覆盖不了长尾。
- **稳定性默认不测**（`--repeat 3` 才开），因为成本×3。
- **忠实度靠 LLM judge**，本身有误差，且每次跑结论会漂。同一题我跑过 4 遍，
  ungrounded 在 0~2 题之间波动 —— **单次数字不能当结论，要重复取分布**。
- **过程管控只能验"该调的调了没有"**，验不了"参数对不对"。要验参数得给每个工具写 schema 断言。
- **没有工具副作用类场景**（下单、发邮件）。当前语料只有查询类工具，
  笔记里"说下单成功但实际失败"那类问题，这套框架有能力测但没数据测。

## 4. 复跑

```bash
.venv\Scripts\python.exe eval\agent_eval.py                  # 七维全量
.venv\Scripts\python.exe eval\agent_eval.py --repeat 3       # 加稳定性
.venv\Scripts\python.exe eval\agent_eval.py --only a-04      # 单题调试
.venv\Scripts\python.exe eval\agent_eval.py --no-judge       # 跳过 LLM 判定，省调用
```
